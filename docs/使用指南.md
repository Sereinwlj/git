# Mini OJ 使用指南

面向"我要用它练手、并且要拿它去面试"的用法。分五块：**跑起来 → 点着用 → 加自己的题 → 改成自己的 → 出问题怎么办**。

---

## 一、跑起来（30 秒）

打开终端，执行：

```bash
cd D:\自做项目\第一个项目\oj
python run.py
```

看到这几行就成功了：

```
[oj] 已从 ...\problems 同步 3 道题目
[oj] worker 线程已启动：4 个
[oj] 服务已启动： http://127.0.0.1:8000
```

然后浏览器打开 <http://127.0.0.1:8000>。

**前置条件只有一个**：`g++` 在 PATH 里（用来编译 C++ 提交）。Python 提交用当前解释器，不需要额外装。

停止服务：终端里按 `Ctrl+C`。

常用参数：

```bash
python run.py --port 9000        # 换端口（8000 被占用时）
python run.py --workers 8        # 并发判题数，按 CPU 核数调
python run.py --sandbox docker   # 换容器沙箱，见第六节
```

## 二、网页上怎么操作

页面分三块，从左到右：

**左侧 · 题目列表** —— 点一下任意题目，右边就会切换成这道题的题面和限制。

**中间 · 代码区** —— 流程是：

1. 选语言（下拉框里是 `C++17` 和 `Python 3`）
2. 点 **「填入示例代码」**，会往编辑框里塞一份这道题的正确解 —— 先点一下，确认整条链路是通的
3. 点 **「提交判题」**
4. 下方 **「判题结果」** 卡片会自动刷新（每 500ms 轮询一次），几秒内出结果

**左下 · 提交记录** —— 当前这道题最近 10 次提交的 id、状态、耗时。

判题结果卡片会显示：状态、信息、耗时/内存。如果挂了，还会列出**每个测试点分别是什么结果** —— 这是排查"第几个点挂的"最直接的方式。编译错误会把编译器原始输出整段贴出来。

### 十种状态的含义

| 状态 | 含义 | 通常的错因 |
|---|---|---|
| `Accepted` | 全部测试点通过 | —— |
| `WrongAnswer` | 输出和标准答案不一致 | 逻辑错，或没处理边界 |
| `TimeLimitExceeded` | 超时 | 算法复杂度不够 |
| `MemoryLimitExceeded` | 超内存 | 开了过大的数组 |
| `OutputLimitExceeded` | 输出超限（默认 1MB） | 死循环里打印 |
| `RuntimeError` | 非零退出码 / 被信号杀 | 数组越界、除零、栈溢出 |
| `CompileError` | 编译失败 | 语法错误，信息里有 g++ 原文 |
| `SystemError` | 评测机自身异常 | 少见，看终端日志 |

`Pending` / `Judging` 是中间态，前端轮询到终态（`is_final`）才停。

## 三、不开浏览器：命令行提交

调试脚本、或者想批量提交的时候用这个。PowerShell：

```powershell
$body = @{
  problem_id  = "1000"
  language    = "cpp"
  source_code = "#include <iostream>`nusing namespace std;`nint main(){long long a,b;cin>>a>>b;cout<<a+b;}"
} | ConvertTo-Json

$r = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/submissions" -Method Post `
     -Body $body -ContentType "application/json"
$r.id                                    # 拿到 submission id
Invoke-RestMethod "http://127.0.0.1:8000/api/submissions/$($r.id)"   # 查结果
```

curl 版本（注意 `\n` 要写成换行转义）：

```bash
curl -X POST http://127.0.0.1:8000/api/submissions \
  -H "Content-Type: application/json" \
  -d '{"problem_id":"1000","language":"cpp","source_code":"#include <iostream>\nint main(){long long a,b;std::cin>>a>>b;std::cout<<a+b;}"}'
```

全部接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/problems` | 题目列表 |
| GET | `/api/problems/{id}` | 题目详情 |
| GET | `/api/languages` | 支持的语言 |
| POST | `/api/submissions` | 提交，返回 `{"id": N}` |
| GET | `/api/submissions/{id}` | 查判题结果 |
| GET | `/api/submissions?problem_id=&limit=` | 提交记录 |

## 四、加一道自己的题（最常用）

**题库是"文件即数据"，不需要写任何 SQL，也不需要改代码。**

### 步骤

**1. 在 `problems/` 下新建一个目录。** 目录名随便起，但建议 `id-简短英文名`，比如 `1003-shortest-path`。

**2. 在目录里写 `problem.json`：**

```json
{
  "id": "1003",
  "title": "单源最短路",
  "description": "给定 n 个点 m 条边的有向图，求 1 号点到 n 号点的最短距离。\n\n输入格式：\n第一行 n m\n接下来 m 行，每行 u v w\n\n输出格式：\n一个整数，表示最短距离；不可达输出 -1\n\n数据范围：\n1 <= n <= 1e5, 1 <= m <= 2e5, 0 <= w <= 1e9",
  "time_limit_ms": 1000,
  "memory_limit_mb": 256,
  "output_limit_kb": 1024,
  "checker": { "type": "exact" }
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `id` | **题目编号，全局唯一**，前端和数据库都用它。注意它是字符串，不填默认取目录名 |
| `title` | 题目标题。不填默认取目录名 |
| `description` | 题面，`\n` 换行。前端会原样展示 |
| `time_limit_ms` | 时间限制。不填用全局默认 1000ms |
| `memory_limit_mb` | 内存限制。默认 256MB |
| `output_limit_kb` | 输出体积上限。默认 1MB |
| `checker` | 比对方式，见下方。不填默认 `{"type": "exact"}` |

**3. 在目录里建 `data/`，放测试点。** 命名规则：`1.in` 配 `1.out`，`2.in` 配 `2.out`，数字会按大小排序；`.in` 找不到同名 `.out` 会被忽略。

```
problems/1003-shortest-path/
├── problem.json
└── data/
    ├── 1.in
    ├── 1.out
    ├── 2.in
    └── 2.out
```

**4. 重启服务。** 题库在启动时扫描一次，加题后必须重启才生效。

### 三种比对器

| `type` | 参数 | 用在什么题上 |
|---|---|---|
| `exact` | 无 | 绝大多数题。逐行比对，**忽略行尾空格**，比较宽容 |
| `float` | `"eps": 1e-6` | 浮点答案题，例如 `{"type":"float","eps":1e-6}` |
| `script` | `"path": "checker.py"` | Special Judge，多解题 / 构造题 |

`script` 类型的调用协议：

```
python checker.py <输入文件> <用户输出文件> <标准答案文件>
退出码 0 表示通过，非 0 表示不通过；stdout 内容会作为失败原因展示给用户
```

现成范例在 `problems/1002-max-subarray/checker.py`。它做的事值得抄一遍思路：**多解题不能"比对"，只能"验证"**。

它校验三件事：
1. 输出的区间是否合法（`1 <= l <= r <= n`）
2. 这个区间的和，是否等于用户声明的那个值（**证明用户没撒谎**）
3. 用户声明的值，是否等于全局最优解（**证明用户真求出了最优解**）

第 3 条是关键 —— 前两条只能证明用户自洽，加上第 3 条才能证明正确性。这就是 Special Judge 的精髓。

## 五、把它改成你自己的（面试前必做）

跑通它是"会用"，改过它才是"我的项目"。**面试官问的是你改了什么。**

按难度从低到高，建议至少做完前三个：

**① 加一道你自己出的题**（30 分钟）
比如从你竞赛里挑一道题，配上测试点。这一步让你彻底搞懂数据是怎么流转的。

**② 加一门语言**（30 分钟）
打开 `oj/judge.py`，找到第 52 行的 `LANGUAGES`，照着 `cpp` 加一条：

```python
    "java": Language(
        id="java",
        display="Java 17",
        source_name="Main.java",
        compile_cmd=["javac", "{src}"],
        run_cmd=["java", "Main"],
    ),
```

`Language` 是个 dataclass，五个字段的含义：`id` 提交时用的标识、`display` 前端下拉框显示的名字、`source_name` 源码落盘的文件名（**Java 必须是 `Main.java`，因为类名要和文件名一致**）、`compile_cmd` 编译命令（`None` 表示解释型语言不用编译）、`run_cmd` 运行命令。命令里的 `{src}` 会被替换成源码路径、`{exe}` 替换成编译产物路径、`{python}` 替换成当前解释器。

加完重启就能提交 Java。**面试官问"你们系统支持哪几门语言、加一门要改多少代码"时，你可以回答"在 LANGUAGES 里加一个条目，判题流程一行不用动"** —— 这是能体现设计水平的回答：语言的定义和判题流程解耦了。

加完记得前端下拉框也会自动多一项，因为它是从 `/api/languages` 动态拉的，不用改 HTML。

**③ 改一个资源限制，观察判题行为变化**（20 分钟）
把某道题的 `time_limit_ms` 改小到 10ms，看原来 AC 的代码变成 TLE；把 `output_limit_kb` 改到 8KB，看输出多的解法变成 OLE。这比背书更能理解"限制是怎么生效的"。

**④ 深入改造方向**（选一到两个，2–3 天）
- 把前端 500ms 轮询换成 **SSE** —— 体验提升明显，且是"我知道现在方案的缺陷"的证据
- 加 **Redis 队列** —— 让判题可以多机水平扩展
- 用 **WebSocket** 做实时榜单
- 加 **限流 + 简单用户系统** —— 现在任何人都能刷爆队列，这是个真实的洞

每改一处，都在 `README.md` 里记一句"改了什么、为什么"。**面试时"我发现了什么问题、怎么改的"比"我实现了什么功能"更有说服力。**

## 六、换 Docker 沙箱

本地沙箱只适合演示 —— 它在 Windows 上只能挡住死循环和无限输出，**挡不住读写宿主文件系统和外联网络**。

要真正隔离，先启动 Docker Desktop，然后：

```bash
python run.py --sandbox docker
```

Docker 沙箱一次性收口了这些限制：

```
--network none          禁网
--read-only             根文件系统只读
--pids-limit            防 fork 炸弹
--memory / --memory-swap 内存硬限
-u nobody               降权运行
no-new-privileges
```

如果配置了 docker 但 Docker 没运行，服务会**自动降级到 local 并打警告**，不会直接崩 —— 这是"可用性优先"的取舍，也是个可以讲的点。

镜像默认 `gcc:13`，可用 `OJ_DOCKER_IMAGE` 换。

**测试沙箱是否真的挡住了恶意代码**，可以往某道题提交这些（谨慎，本地沙箱下真的会执行）：

| 攻击 | 本地沙箱 | Docker 沙箱 |
|---|---|---|
| `while(1);` 死循环 | ✅ 靠 wall clock 挡住 | ✅ |
| 无限 `cout` | ✅ 输出超限 | ✅ |
| 读 `/etc/passwd` | ❌ Windows 下挡不住 | ✅ 只读文件系统 |
| `system("rm -rf /")` | ❌ | ✅ 降权 + 只读 |
| fork 炸弹 | ❌ Windows 无 ulimit | ✅ pids-limit |
| 外联下载脚本 | ❌ | ✅ network none |

这张表是面试时的**加分题**：能主动说出"我的方案在什么场景下不够用、应该换什么"，比声称"我的沙箱很安全"可信得多。

## 七、出问题怎么办

| 现象 | 原因与处理 |
|---|---|
| 端口被占用（`Address already in use`） | 换端口 `python run.py --port 9000`，或先杀掉旧进程：`Get-NetTCPConnection -LocalPort 8000 -State Listen \| Select -ExpandProperty OwningProcess \| Stop-Process -Force` |
| C++ 提交全变编译错误 | `g++` 不在 PATH。终端跑 `g++ --version` 确认 |
| 提示**编译错误，看不出原因** | 结果卡片里 `<pre class="err">` 那段是 g++ 原文。Windows 的 MinGW 用 `bits/stdc++.h` 时**不自动引入 `std` 命名空间**，记得写 `using namespace std;` 或加 `std::` 前缀 |
| 觉得答案对但判 WA | 打开调试开关（见下），去 `runtime/` 里看它实际喂了什么输入、你的程序输出了什么 |
| 提交永远停在"判题中" | 服务可能挂了。看终端有没有异常。重启服务后，它会把 `Pending/Judging` 的提交**自动捞回来重判** |
| 想重新开始，清掉所有历史 | 关掉服务，删除 `oj.db` 和 `submissions/` 里的文件，重启即重建 |

### 调试开关：保留判题现场

排查误判时打开它，判完不删临时文件：

```powershell
$env:OJ_KEEP_RUNTIME = "1"
python run.py
```

然后每个提交的现场都躺在 `runtime/submission_<id>/` 里：

```
runtime/submission_31/
├── main.cpp       你提交的源码
├── main.exe       编译产物
├── _user_out.txt  你的程序实际输出
└── ...
```

配合 `submissions/<id>.cpp`（所有提交的源码存档），可以完整复现任何一次判题。

**排查完记得删掉 `runtime/` 里的残留目录** —— 不清会一直堆着。

### 判题日志

服务启动的终端里，任何异常都会打印堆栈。判题是在 worker 线程里跑的，所以**出错不会中断服务**，只会让那一次提交变成 `SystemError`。

## 八、关于 Windows 上的一处已知限制

本地沙箱在 Windows 下**只能靠父进程观察 wall clock 来判超时**，无法限制 CPU 时间、内存、fork 数量（那些依赖 POSIX 的 `setrlimit`）。

具体影响：
- 死循环能被拦住，但**多线程疯狂占 CPU 的程序拦不住**
- 内存超限的判定是启发式的，可能不准
- 恶意代码在本地沙箱里是真的能跑起来的

这是"跨平台可用性"换来的代价。**真要判不受信任的代码，必须用 Docker 沙箱。** 这一点我在 README 的"已知不足"里也写了 —— 主动说出方案的局限，比假装它没有局限要好得多。
